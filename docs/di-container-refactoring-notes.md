# DI 容器重构经验

本记录来自容器解析路径的设计调整，用于后续重构参考，不是最终功能规格。除文末列出的独立基准外，以下性能判断不视为已验证；不将代码更短、分支更少或使用 BCL 等同于执行更快。

## 先调整职责和约束，再调整代码

- 从实际使用方式出发，不为尚未出现的需求保留生命周期、对象来源或策略体系。允许以后根据具体需求重新设计。
- 分离构建期输入和运行期状态。类型存在大量只在某阶段使用或永远为空的字段时，先检查是否混合了不同职责，不急于增加派生类型或中间类型。
- 构建阶段能确定的映射与归属可以提前处理；运行期不必反复推导。提前创建描述或 Lazy 不等于提前创建服务实例。
- 复制查找表不等于复制实例，也不转移所有权。共享父层数据时，本层覆盖应建立自己的存储，不能修改父层列表。
- 改变查找结构前明确优先级，尤其是精确匹配、开放泛型、本层覆盖和集合之间的关系。结构优化不能悄悄改变行为。

## 简化看完整流程，不追求形式统一

- 目标是职责直接、调用链短、分支浅、总体实现简洁，不是强行让不同路径使用相同类型或接口。
- 两种来源的数据和处理方式明显不同，可以在入口提前分开，减少后续判断和无效字段。少量直接重复可以比统一包装更清楚。
- 不为普通项、多项和泛型增加带多个可空字段的包装，仅仅换取快速路径。新增类型必须实际减少整体复杂度。
- 正常业务中的并列互斥路径优先用 `if/else` 表达；跳过无关项或提前结束才使用 `continue`、`return`。少一层缩进不一定更易读。
- 能放在循环外的条件判断移到循环外，避免每轮重复决定相同的处理方式。
- 不把空值赋值、条件表达式和对象创建叠在一个表达式里。缓存命中与对象来源判断可以分别表达。

## 方法提取与内联

- 短小、单处使用的转发或判断优先考虑内联，查看能否同时消除中间变量和重复分支。不要仅为了给几行代码命名而增加调用层。
- 本地函数适合封装单个方法内真正复用的流程。例如识别到不同集合形式后直接调用集合解析函数，避免先设置可空元素类型再判空。
- 不机械地将所有单处调用改为本地函数，也不机械地全部内联。以阅读完整流程所需的跳转、重复和嵌套为判断依据。
- 若两个入口只有失败语义不同，保留共享核心实现有实际价值。当前 `Resolve` 和 `TryResolve` 共用解析，避免先查询是否存在、再重复解析。
- 捕获变量不等于堆分配。直接调用的本地函数与转换为委托、交给 Lazy 保存的函数应分别分析；不要为了避免捕获强制传递所有状态。

## 使用 BCL 与处理失败

- 已有 BCL 类型准确表达所需行为时，优先替代手写状态管理。替换前确认异常缓存、递归访问、线程模式和所有权语义。
- 外部已有实例直接使用 `Lazy<object>(instance)`；需要创建的实例使用工厂委托。避免为已有值建立不必要的工厂和捕获状态。
- `CollectionsMarshal.GetValueRefOrAddDefault` 适用于查找并插入，不用于纯查询。不要跨递归解析持有或使用字典元素引用，递归可能使字典扩容。
- `group ??= []` 与 `out exists` 关注点不同：前者判断值，后者判断键是否存在。只需确保非空值时使用短且直接的写法，不假定其中一种更快。
- 方法包装不等于额外字典查询，`try/catch` 也不等于正常路径发生异常。性能讨论应指出具体重复操作或分配，实际收益留待测量。
- 一般不使用断言；错误输入可能被误当作成功时必须校验，否则通过文档说明约定。无法完成解析、循环依赖、构造或注入失败仍需传播异常。
- 仅用于附加诊断信息的异常包装，根据实际定位需求决定是否保留，不默认逐层包装。

## 本轮采用的具体取舍

- 保留 RootScope 与 SceneScope；去掉 Transient、Scoped 和 Lifetime。注册位置决定实例归属，内部实例由所属容器释放，外部实例由外部管理。
- 普通注册直接保存 Lazy；开放泛型使用专用模板与闭合实例缓存，不引入 Provider。别名共享同一 Lazy 或泛型模板。
- 构建时读取 RegistrationBuilder，不保留其引用；重复 Build 生成独立的内部状态。
- 子容器持有合并后的可见映射；同键本层注册覆盖父层整个列表，精确类型注册始终优先于开放泛型注册。
- 无 Key 的 IResolver 固定为当前容器，通过注册表表达，不在解析中增加特判。
- 集合统一通过 Resolve 解析，删除 ResolveAll；自动集合仍根据当前可见元素注册生成数组，不强行归入普通泛型模板。
- Lazy 使用串行模式，接受创建失败被缓存；删除手写 ServiceEntry 和 ResolutionException 包装。

这些是当前需求下的选择，不应推广为所有容器必须遵循的限制。后续职责变化时同步调整名称，让名称表达当前存储和行为，不沿用已经删除的 Entry 等概念。

## 后续调整时的检查顺序

1. 明确需要保留的行为，以及允许改变的约束。
2. 判断是否可以删除职责、字段、入口或中间表示。
3. 展开实际调用路径，检查重复查询、短小转发、分支位置及所有权。
4. 选择直接分路或共享实现，以总体阅读成本决定。
5. 同步调整命名；在用户安排的验证阶段确认行为和性能，不提前声称收益。

## 后续收敛与验证

- 构造和成员分析统一放在 InjectionAnalyzer；Dependency 保持纯数据，参数数组直接由调用方保存，不保留 ConstructorInjection 与 ParameterBinding 包装。
- MemberInjection 使用 required init 具名初始化。类型创建与工厂创建直接返回对象，由调用方包装 Lazy；分析在首次解析时执行。
- 工厂属于容器创建，返回值由所属容器缓存并释放，不自动成员注入；外部实例仍由外部管理。
- 普通构造函数、主构造函数和 required init 的独立基准显示相同实例分配量；读取生成等价指令。该结果只针对所测对象布局及运行环境。
- Dictionary 与 FrozenDictionary 的复合键基准未提供足够依据支持统一替换，当前保留普通字典。
- 基准源码见 [初始化比较](../benchmarks/Xoderony.Benchmarks/Initialization/InitializationBenchmarks.cs) 与 [注册表比较](../benchmarks/Xoderony.Benchmarks/DependencyInjection/RegistryDictionaryBenchmarks.cs)。微基准结果不能替代完整容器负载验证。
